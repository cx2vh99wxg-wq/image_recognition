## 第二阶段：独立掩膜只冻结一次

`M/pcie/include/latest_lane_worker.h`：正式直达 IPM 路径中，NPU 所有者将输出一次复制到当前 `Snapshot` 的独立向量；CPU 后处理、同帧行人道路关联及发布后的只读快照共用该向量。原来 CPU 分析还会再复制一次约 0.92MB 的模型掩膜，现在省去这一次。备用非直达路径保留。没有引用下一次推理会覆盖的 SDK 缓冲区，也没有在发布后继续修改向量。

同帧校正图也核对过：交通灯/行人的 `prepare_lane` 已直接使用该任务的校正后 320×240 图，只做既有 BGR→RGB 复制，没有再次执行畸变校正。独立颜色跟踪邮箱仍按自己的更新节奏接收较新图像，不能用旧的车道图替代并误称“同帧复用”。本轮保留该分工。

新增直接 IPM 分支的实际工作线程测试：在可选任务中故意覆盖模型缓冲区，两个消费者仍读到原值；确认行人道路指针与发布快照的自有向量相同。该测试在私有 IPC namespace 运行，不替换实时斑马线元数据。

旧版与新版各运行四张保存画面的生产 `LatestWorker`＋两个真实模型（每张还比较串行和并行）。原始/恢复掩膜逐字节相同，五点、方向/角度、两侧线型、前方行人风险/路外/不确定统计相同。新第二张为避免误用旧图，从最新校正输入构造专供回归的原始拼接图；它不是一次新的摄像头拍摄。

90 秒完整负载复测：M 视频 **30.00FPS**，新车道结果 **4.506 次/秒**，服务 **4.504 次/秒**，CPU 分析均值 **15.62ms**，模型核心 **190.46ms**；S 显示 **29.946FPS**，最低五秒窗口 **29.59FPS**。前一阶段 M 分析约 16.52ms、新车道 4.492 次/秒；CPU 有节省，新结果频率只小幅变化，不能把这项优化说成模型推理大幅提速。

部署证据：`output/system-round2-20261110/M-copies`，其中 `M-copy-regression.json` 记录四图旧新相等结果。两块板均恢复正常视频/元数据流程后才计时，没有把离线测试时 M 停发的视频空载 FPS 当作验收。

## 第三阶段：S 视频保留 RGB565，仅推理帧展开

S 原来每帧把 RGB565 展开 RGB888、旋转、绘框，再压回 RGB565。现在直接旋转 RGB565、在原生像素上绘框和执行等价的缓存告警混色，只在真正提交人员模型的帧上展开 RGB888。密集人员等非缓存路径仍使用原浮点混色，避免改变原有叠加结果。保留 `S_VISION_NATIVE_565=0` 对照开关，默认启用新版。

`test_native_overlay` 在实际 ARM 板通过：40 组框、裁切、闪烁相位、密集人员输入，最终显示像素逐字节一致；模型输入像素逐字节一致，源图与边界哨兵不变，控制人员统计未改。相同四人受控 CPU 微基准从 **7.29ms 降至 5.06ms（约 31%）**，不把这当作整机提升百分比。已有末行修复、相机 0 的绕行修复、DMA 等待、推理提交间隔和原制动规则均保留。

完整运行前 90 秒 / 后 100 秒：S 显示 **29.924 / 29.950FPS**，后最低五秒窗口 **29.61FPS**，无完成超时、过期结果或工作线程失败。当前静态负载下显示已接近 30FPS，不能宣称显示速率显著提高；节省的是采集 CPU 余量。新版采集循环约 **34.4 次/秒**、人员推理约 **11.4 次/秒**，循环速率不是相机物理曝光采样率。M 同期视频 **30.002FPS**，车道 **4.50 次/秒**，CPU 分析 **15.53ms**，核心推理 **190.40ms**。不同阶段窗口略有波动，不据此承诺所有动态场景不掉帧。

四张保存图片的实际 S 模型人员统计在部署前后仍完全相同。S 控制端仅恢复原 `--brake-only` 监视流程，M IMU 和自动转向未启动。板上源文件及可执行文件哈希核对通过。

## 第四阶段：动态延迟与显示压力回归

M 使用生产 `LatestWorker`、交通灯/行人服务和两个真实 RKNN，在私有 IPC namespace 中以 30Hz 提交保存的四图并切换。116 个新车道结果，**4.659 次/秒**；读取时结果年龄中位数 **233.33ms**，P95 **266.71ms**，最大 **267.15ms**，过期结果为 0。632 次待处理帧覆盖是有界“保留最新帧”邮箱的预期行为，不是推理结果丢失。所有人员结果的道路掩膜帧号与检测帧号相同。

前三张的每阶段末段均稳定为绿灯并报告危险行人；第四张保留多方向灯色的歧义状态，没有强制当作绿灯。不同切换阶段达到预期灯状态的时间约 **0.33～2.17 秒**（第一阶段约 0.37 秒）。这是整套检测/跟踪状态的重获时间，与单次模型耗时及车道结果年龄不同，后续仍值得专项改进；本轮没有为了提速删掉歧义或状态保护。

这组四图主要是交通灯与斑马线场景，不是连续道路转向真值集。S 另用保存图像驱动真实 X11 呈现，持续改变角度（约 5Hz）、虚实线、灯色、红白闪警、四个人物步态，并切换六路/单路视角。测试复制的渲染器只允许预览输入，不写入任何真实控制 IPC；结束自动恢复正常渲染程序。预热后 900 帧 **29.867FPS**，工作时间中位数 **30.88ms**、P95 **37.91ms**，帧间隔 P99 **50.08ms**、最大 **67.18ms**。平均接近 30 不等于每一帧都小于 33.3ms；本轮仍有长尾，不能保证所有场景绝不短时掉帧。

## 第六阶段：俯视图真实漆线证据的缓存试验

现有实虚线程序已经沿俯视标线法向读取真实漆线及两侧背景，按弧长统计漆段/空隙；阴影弱证据与 IPM 无覆盖分开，几何插值不充当白漆证据。保持这套规则，试验每条线的 1024 槽像素缓存，以复用重复 RGB/亮度读取。

受控白/黄线、阴影、斜线、横向偏差、无覆盖和裁切测试通过，15 张真实模型掩膜的两侧线型输出与原版完全相同。但三次微基准均值从 **1.122ms 变为 1.306ms**，约慢 **16%**；缓存初始化、查找成本超过重复读取的节省。**拒绝采用**，未改正式实虚线判断或其即时生效规则。

## 第八阶段：DMA 同步与驱动审计

核对用户态 ABI、现有控制 RTL 和板上 `6.1.99` 驱动。ABI 有分开的 DMA 提交/读回和全局 MSI 标志，没有已验证的逐请求完成序号或缓冲归属协议；RTL 中 `*_cfg_done` 是配置接收完成，不能作为主机内存已可安全读回的证明。模块符号检查也不能代替完成语义文档与压力测试。

因此本轮**没有合并读写 ioctl、缩短 M 10µs/S 8µs 读回保护、改驱动或 FPGA**。保留现有末行、包边界、相机绕行修复。必须先建立可靠完成条件，再做合并传输；这是此次审计后未采用的方向，不能写成已完成驱动提速。

## 第九阶段：只因绘制像素变化才重画车辆层

S 车辆图层缓存原来会因未被绘制的细微分值变化而失效。现在只在缓存键中忽略人物分值；车道分值按实际绘制所用的 `>=60` 有效/无效分档比较，曲线类型由已计算的角度和有效性表达。原始分值、曲线类型仍原样存储，未改检测、追踪、选择阈值、IPC、角度或制动规则。人物位置、尺寸、道路关联标志、地面坐标、步态和闪烁变化仍使缓存失效。

提取 `vehicle_layer_state.h` 供同一份缓存键接受测试。41 组分值变化的实际车辆/车道/人物绘制逐像素相同；12 个影响绘制的字段改变均使缓存失效。四人只改变分值的微基准：原重复重画约 **1.092ms**，复用判断约 **0.639µs**；该结果只说明特定无像素变化场景的节省，不是整机加速倍数。另将正式渲染器 Makefile 固定为单一 `main.cpp` 入口；诊断源使用独立目录，避免通配源文件误把回放工具链接进正式程序。

新程序部署后，四张保存图片的真实人员模型统计仍一致。再次使用真实 X11 窗口，额外加入每帧分值抖动，保留转角、灯色、步态、闪警与视角切换：900 帧平均 **29.894FPS**，工作时间中位数 **27.08ms**，P95 **37.27ms**，帧间隔 P99 **49.77ms**，最大 **64.29ms**。比前一次工作时间中位数小，但输入负载和系统状态并非严格相同，不能把全部差值归因于缓存键；逐像素回归和专门微基准才是其直接证据。

末行回归：M 正常运行 60 秒、1,801 个发布帧，约 **30.00FPS**，读回错误、尾行不一致、黑白棋盘闪点计数均为 **0**。没有直接访问或写入 DMA/FSPI。原 Auto Brake、路内/路外/不确定保护、绿灯加三次独立无人恢复、红灯独立阻止前进和实线变道规则，在私有 IPC 与模拟传输的控制回归中通过；这不是实车机械制动距离测试。
