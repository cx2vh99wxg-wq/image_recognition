# 2026-11-10 整机优化、回归与未采用候选

> 后续变更：用户随后要求撤销交通灯的其他类别竞争排除；该项已撤销，单次颜色确认保留。同帧 CPU/NPU 重叠现已实现并部署，实测收益及限制见 [本轮重叠报告](cpu_npu_overlap_20261110.md)。下文保留当时版本的测量和结论，不作为后续版本仍未实现这些功能的说明。

本轮以 `better` 的 `e54ae176` 为提交基线，接续尚未提交的人物显示与交通灯修复。实验仅使用两块板上的 Linux，以及 E 盘保存的数据；没有使用 Ubuntu 虚拟机，没有修改 FPGA、SFC、引脚或 DMA 等待参数。

“尝试优化”与“采用候选”分开记录。候选更快，但改变了道路掩膜、实虚线或行人道路关系时，不自动替换正式版本。现有保存数据只有三个独立道路场景和三张交通灯实拍图，不能据此证明所有场景准确率不下降。

## 功能要求

已按要求改为：一个新鲜、通过目标/结构和颜色检查的交通灯结果立即有效。不是任何红色或绿色像素都有效；重复帧、旧帧、冲突和无合格证据仍不能通过。`traffic_vision.h::ColorConfirmation` 不再累计颜色确认次数。

YOLO 类别竞争筛选保留：其他类别分数更高时，那个 YOLO 候选不会因为具有红绿颜色而成为交通灯。手机图示漏检的结构定位见 `traffic_signal_repair_20261109.md`，它另行要求三盏圆灯、未亮圆灯边缘、间距和灯壳；没有降低 YOLO 分类门限。

前方行人刹停阴影由 S 显示读取既有 `FrontGuardData`：状态新鲜、Auto Brake 开启且现有 `raw_request` 生效，才把原有有效角度上方填充从绿色变成红色。显示代码不重新判定行人、不写控制记录、不推进恢复计数、不解除 STOP。无有效当前角度时仍沿用既有灰色历史车道显示，没有凭空增加道路区域。

保持以下规则：

- 行人框与可行驶区域同帧关联；路内或不确定时保持保护，明确路外不触发前方保护。
- Auto Brake 开关控制是否自动制动。
- 绿灯加三次不同的新鲜无危险观察恢复前进许可；重发同一结果不算三次。
- FPGA STOP 仍只能人工 REARM。
- 实虚线、左右边界、五中点、曲率、低曲率 30° 门控、方向正负及转向角换算未借性能优化修改。
- IMU 和 `vehicle_control` 保持关闭；本轮没有带动车辆做实车刹停测试。

## 已采用的优化

### 交通灯 / 行人输入准备

`M/pcie/include/traffic_letterbox.h`：320×240 到 320×320、缩放系数恰为 1 时，填充 114 边框并逐行复制，替代逐像素浮点双线性插值；其他尺寸和缩放继续走原计算。回归逐字节比较模型输入，覆盖有行跨度和一般缩放路径。

板上微基准约 **5.3883 → 0.1748 ms**。整机交通灯/行人服务约 **17.6 → 12.5 ms**；微基准不等于整机识别周期，不能把节省的 5 ms 说成 YOLOPv2 推理翻倍。

### 共用车道逐行点集

`latest_lane_worker.h` 在 IPM 后只生成一次只读 `LaneMaskRows`，传给 `select_point_lanes` 和 `marking_profile`。两套连接规则继续分别运行；没有把推测补点当作真实油漆。

11 帧真实俯视掩膜回放中，共用与各自扫描的几何、角度、样点及线型相同。样例 CPU 微基准 **0.9505 → 0.4652 ms**。这是扫描和分配优化，不是更换选线算法。

### 控制元数据不再等待完整视频

`M/udp/csrc/main.cpp::MetadataPump` 在视频的有界行批次之间、空闲时轮询新结果。语义变化立即发送独立小包，同时保留心跳。转向使用有版本、会话、帧号、结果年龄和校验的 `CVP1` 小包；人员、灯和线型沿用各自协议。

S 的独立小包和视频元数据共用既有 `CurveReceiverState`，不让重复帧续期。退役会话、校验、边界、失效和兼容视频均有回归。单线程持有 IPC 读者，避免为了“立即发送”引入源句柄竞争。

实测轮询平均间隔约 **3.2 ms**；这是发送端轮询间隔，**不是端到端制动延迟**。没有测得的数据不填作延迟承诺。

### S 显示与计时

默认使用 XShm 完成事件，按共享段、请求序号、目标和偏移匹配后才复用图像；250 ms 有界等待失败回到同步路径。没有删除缓冲区归属保护。

显示循环等待计入已经花掉的绘制时间，慢动画帧不再额外固定睡 16.7 ms。增加有界的提交间隔 P50/P95/P99/最大值，以及交通服务输入准备、提交、NPU、取输出、解码、释放和筛选计时。

同负载 A/B/A：原同步 **21.185**、完成事件 **24.265**、恢复原同步 **21.435 FPS**，因此保留完成事件。实际应用窗口是 **1920×1080**；3280×1280 是含 DSI 的虚拟桌面，不能混为应用窗口大小。

240 帧动态 UI CPU 回放涵盖连续角度、四个行人、实虚线、红白告警、三色灯和刹停阴影：P50 **18.759 ms**、P95 **20.995 ms**、P99 **22.436 ms**。这是 CPU 绘制时间，未包含真实 X11 呈现，不能叫作屏幕 FPS。

最终追查到 Xfce 桌面合成器还在对不透明全屏画面再次合成。它与应用内部绘制车道、人物或半透明阴影的过程不同。实测保持同一显示程序、同一完整 M 输入，关闭该合成器后中位数 **24.165 → 29.985 FPS**，最低五秒窗口 **28.90 FPS**。恢复合成器又触发了原图形驱动的同步回退，恢复段不能作为纯性能对照；采用前重新启动原显示程序以清除回退状态，另作最终连续验收。

S 的 `scripts/compositor_policy.py` 只设置当前 Xfce 用户的 `/general/use_compositing=false`，`scripts/prepare_display.py` 在正常 `make run` / `make run-display` 时应用，M 启动不受影响。没有改变 HDMI、DSI、摄像头、模型或控制逻辑。桌面窗口阴影等合成器效果会关闭，应用自身的透明阴影照常由自己的渲染代码生成。`VISION_KEEP_COMPOSITOR=1` 可跳过设置；需要恢复桌面合成时，以同一桌面用户运行 `xfconf-query -c xfwm4 -p /general/use_compositing --set true`。脚本检查设置结果，查询不可用时保留桌面状态，不因此阻止识别程序。

## 模型、量化和训练

### YOLOPv2

正式保留 FP16 320×240（网络内部仍按原接口补边）的 RKNN，SHA256：

`4f0e9eb2c0eeb36ff9107803417ee57943939d2cb0b76edfc722773045674499`。

新增 stem+heads 混合候选保留首部六个特征块及分割头的 FP16，约 117 个配置项。耗时 **195.47 → 123.22 ms**，11/11 帧几何和线型一致，但模拟脚部采样中有 3 个位置从保护类变为路外，未替换。没有人工真值，不能把它写成“漏检 3 个人”。

通过 Toolkit IR 重新构建后，**243 层精度分析成功**，保留单层/累计误差报告。上述 stem+heads 候选先于逐层分析构建；随后另做真正按误差排序的候选：额外保留单层余弦误差较大的 `/model/32/`、`34/`、`51/`、`20/` 四个块，从 117 增至 145 个 FP16 配置项。约 **134.94 ms**，几何与线型均 11/11 相同，但仍有一个模拟脚部位置保护→路外，**不采用**。这说明方向相同仍不足以证明行人道路关联等价；没有宣称找到了最优混合策略。

QAT：从 ONNX 重建约 2451 万参数可训练网络，FP32 对齐最大误差约 `1.3e-5`；完成 366 个伪量化器、两步 CPU 训练、冻结导出适配及 ONNX 导出。导出适配前后输出完全一致。Toolkit 按较保守的 optimization level 2 转换成功，并跑完 11 帧 NPU/IPM 回放：约 **195.47 → 123.52 ms**，几何 11/11 一致、线型只有 8/11 一致，模拟脚部有 10 个保护→路外变化，**不采用**。转换使用 `build(do_quantization=False)` 导入带伪量化导出节点的 ONNX，没有再次做 PTQ；不能仅凭该 API 参数或测速称其已验证为全层 INT8。两步只验证工具链，不是充分训练的 QAT。

`qat_yolopv2_front_pilot.py` 保存该实验流程；默认两步、不自动提升模型。`convert_front_lane_rknn.py` 新增可选 `--optimization-level 2/3`，默认 3 不变。先前 level 3 长时间构建的私有进程已结束，不影响正式模型。

TwinLiteNet+ Small/Medium、不同输入规模、全 INT8、只保留分割头 FP16、YOLOv8n 的上轮实际板上对照继续有效，见 `model_optimization_20261109.md`。本轮从 84 步学生再训练 516 步，累计 600 步：教师损失约 **0.17682 → 0.08930**，完成 ONNX 等价导出、RKNN 转换和 11 帧正式 IPM 回放。耗时约 **64.38 ms**，但完整几何只 5/11、线型 7/11 与基线相同，模拟脚部有 1964 个保护→路外变化，**不采用**。这些是网格采样位置，不是 1964 个真实行人。损失下降不能证明独立场景改善；没有把缺乏标注的少量重复帧当作正式准确率证明。

### S 人员模型

实际下载并转换 YOLOv5n 640 候选，核对 S 原引擎所需的三个量化检测头、零点和比例，用原解码器测量，而非只改文件名。7 个包含 bus 四格亮度/尺寸变体及空白的输入，两模型人员存在性一致，但不是独立遮挡/远处人员测试集。

线上 A/B/A：原 YOLOv5s640 检测任务约 **72.8 ms**，候选约 **49.8 ms**；显示中位数约 **24.3 → 26.0 FPS**。由于缺真实小行人/遮挡召回验证，已恢复原 YOLOv5s640，SHA256 `3c75dfd25cd152de1fe787544fd40e8b96f6a98b40004b8621cd9ea18def9588`。不以显示变快为由改变制动模型。

## 分析和原型后未修改正式行为的项目

1. **道路成对选择、跨段几何和 30° 门控。** 已在真实俯视掩膜和横移/斜直线合成例上试验。参考道路轴可恢复部分两边界都落在 x=160 同侧的情况；移除 30° 会把一些原本直行改成转弯。它们是算法行为变更，未混入“功能相同”的性能优化。当前选线距离 10 像素、跨度大于 30、五点及 ±3 行找点等规则不变。
2. **上一帧 CPU 后处理与下一项 NPU 工作重叠。** 核对了借用输入和掩膜指针、NPU admission、发布先后和帧号关系。正式系统继续单一 NPU 所有者；本轮没有完成并部署安全的双快照流水线，不能宣称这一项已经完成。
3. **驱动 / FPGA。** 当前 MSI 标志没有可核实的“本次逐行 DMA 完成”语义。M 10 µs / S 8 µs 读回等待、逐行 ABI 和既有像素边界保护不变。未以缩短保护等待换取虚假的提速。
4. **标定。** 记录实际径向和 IPM 配置、相机映射、程序和模型哈希。没有新的多姿态平面数据，未把屏幕/手持纸标定升级宣称为真实路面完整内外参。
5. **数据集。** 复用保存的三个交通灯和 11 帧俯视车道输出；训练/校准没有混入第二、第三道路场景。没有凭空补出 500～1000 张人工标注数据。正式量化、QAT、蒸馏模型仍需要独立标注场景验证。

## 回归与发布

交通灯三色和空白用私有 IPC 跑完整服务；车道用保存的 IPM 掩膜比较；前方行人、Auto Brake、三次独立无人、红灯前进许可、线型变道和失效规则用控制状态测试。没有向正在运行的车辆控制写入测试角度或假绿灯。

`tools/release_manifest.py` 只读记录实际进程、白名单环境选项、模型/程序/标定哈希和时钟；不读取密码或输出完整环境。原始摄像头画面、转换模型、训练依赖、临时 swap 和大张量不进入 Git。

M 闪点修复必须保留 `common/image/camera_valid_rows.h`，正常 M/S 构建均包含 `test-camera-guard`。更换模型或显示路径后的最终检查必须在恢复全部正式程序、关闭试验负载后进行，不能拿 M 停止发送视频时的 S 30 FPS 作为完整负载结果。

## 最终两板同时运行 150 秒

模型、预算和显示试验全部退出，正式 FP16 / YOLOv5s640 恢复、S 桌面合成器关闭后，两板同时运行。每项约 30 个五秒统计窗口：

| 指标 | 最终实测 |
|---|---:|
| M 视频发布平均 / 最低窗口 | 29.999 / 29.87 FPS |
| M 新 YOLOPv2 车道结果平均 | 4.443 次/秒 |
| M 前方行人 / 灯目标检测平均 | 4.437 次/秒 |
| M 目标检测服务平均耗时 | 12.304 ms |
| M YOLOPv2 `rknn_run` 平均 | 190.224 ms |
| S 显示平均 / 中位数 | 29.926 / 29.94 FPS |
| S 显示最低 / 最高五秒窗口 | 29.59 / 30.04 FPS |
| S 接收 M 视频平均 | 29.974 FPS |
| S 显示提交间隔 P99 各窗口平均 / 最大 | 44.56 / 55.69 ms |

S 在关闭合成器前的同轮 150 秒为平均 23.973 FPS、最低窗口 22.42；关闭后平均提高约 **24.8%**，本次 150 秒没有再出现 22～23 FPS 的五秒窗口。提交间隔仍有长尾，所以不承诺每一帧、所有未来负载都固定 30 FPS。S 本地输入读到的是发布/接入频率，不是直接测量 OV5640 的曝光频率。

M YOLOPv2 新结果相对上一轮约 4.22 次/秒小幅提高到约 4.44，约每 **225 ms** 有一份新结果；不是视频 30 帧就推理 30 次。正式模型保留 FP16，不能把未采用的 64～135 ms 模型测速写成当前识别速度。跨轮温度和负载也可能影响小幅频率差；本轮最明确的大收益是 S 显示合成器对照和逐字节等价的 CPU 处理优化。

M 同时运行实时末行检查 60 秒：采样 **1801 帧**、发布 **30.000 FPS**、`read_errors=0`、`tail_bad_frames=0`、`checker_frames=0`。没有回退边界修复。M worker_failed 为 0；S 无完成事件超时。随后 UDP 摘要为 29.99 FPS，incomplete/corrupt/kernel_drop 均为 0；发送失败为 0。

两板可用内存约 M **1303 MB**、S **1241 MB**，swap 为 0。M IMU 为 inactive，M/S 均无 `vehicle_control`。临时训练、编译、下载管理器和转换进程均已退出；候选文件在 `/userdata` 静态存放，不在后台运行。没有使用用户的虚拟机。

**验收范围限制：** 这段线上窗口主要是室内当前画面，不能当作 150 秒覆盖了急弯、人群和交通灯的准确率证明。识别功能另由保存的三色完整服务回放、11 帧真实俯视掩膜、状态机测试和 240 帧动态 UI CPU 回放验证。没有新的独立人工标注，无法给所有模型准确率排名，也没有完成充分训练的模型或正式 CPU/NPU 双快照流水线。
